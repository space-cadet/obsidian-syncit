## Problem

The current planner treats a local-only file as an upload and a remote-only file as a download when no trusted baseline exists. On a new device this cannot distinguish a genuinely new file from a stale copy that was deleted or reorganized on another device. A local sync index does not solve this because it is device-local.

Example: a tablet contains an old `learning chinese` folder while the remote vault reflects a reorganized mobile vault. The first sync currently uploads the stale tablet files.

## Goal

Make first syncs safe and make later deletion decisions reliable across devices without silently uploading stale files or permanently deleting ambiguous data.

## T13a: First-Sync Safety Gate — Implemented

- Added reconciliation items to `SyncPlan` for no-baseline local-only, remote-only, and same-path changes.
- Stopped normal sync and Dry Run from transferring plans that contain ambiguous or possible deletion paths.
- Added sidebar status for "Reconciliation required".
- Fixed in-memory sync-index reuse across server signatures.
- Kept the previous in-memory index when persisting a new index fails.
- Replaced the ineffective settings comparison with a last-persisted server-configuration snapshot.
- Prevented index commits after partial transfer results.
- Serialized index rebuilds against sync and dry-run operations.
- Made the concurrency pool wait for already-started operations after cancellation or rejection.
- Added focused tests for first-sync planning and index signature isolation.

T13a deliberately does not yet provide the choice UI. A blocked plan must be resolved by T13b before transfers can resume.

## T13b: Reconciliation Review and Apply — Implemented

- Added a review panel to the sidebar with every ambiguous path, its reason, and local/remote size summary.
- Added per-item choices: use local, use remote, keep both, or leave unresolved.
- Added first-review policy shortcuts for two-way review, upload-only, and download-only behavior.
- Apply remains disabled until every item has a decision. Cancel makes no file changes.
- Applied choices are revalidated against a fresh scan before transfer; a changed plan returns to review.
- Use-remote choices can remove stale local files through the existing trash/delete setting.
- Use-local choices can restore remote files or explicitly remove remote-only files.
- Keep-both uploads the local conflict copy under a generated sibling path such as `note (local copy).md`.
- Dry-run operation rows now say “Would upload”, “Would download”, “Would delete”, or “Would review”.
- Increased the persistent activity log and reconciliation item list scroll areas.
- Added decision-matrix tests for stale local deletion, remote deletion, keep-both, and download-only behavior.

T13b is a review/apply layer only. T13c is still required for a shared remote manifest and tombstones so a device can reliably recognize deletions made while it was offline.

## Planned Design

### 1. Repair the current state model

- Fix `saveSettings()` invalidation using a real pre-change settings snapshot.
- Make `SyncIndexManager.load()` validate the requested server signature even when an in-memory index exists.
- Treat the local index as a performance cache, not as cross-device authority.
- Commit a new index only after every planned operation succeeds and post-transfer verification passes.
- Do not infer deletion from a missing path unless a trusted shared baseline exists.

### 2. Add explicit sync modes

Add settings for:

- `two-way`, `download-only`, or `upload-only` ongoing sync;
- first-sync policy: prompt, remote-wins, local-wins, or review;
- conflict policy: prompt, remote-wins, or local-wins;
- deletion policy: trash, permanent, or ignore.

The first-sync policy is separate from the ongoing direction. Two-way sync is safe only after reconciliation establishes a baseline.

### 3. Add first-sync reconciliation

- Classify local-only and remote-only paths as ambiguous when no trusted baseline exists.
- Show a review UI before transfers begin.
- Support whole-vault, folder, and individual-file decisions.
- For remote-wins, archive local-only files to Obsidian trash or a review area before downloading the remote state.
- For local-wins, upload the local state after explicit confirmation.
- For review, allow upload, download, archive, keep-both, skip, and cancel per item.
- Keep Dry Run read-only and extend it into a preview/apply flow without silently applying the existing plan.

### 4. Add shared manifest and deletion tombstones

Store a versioned manifest under the remote base directory, outside the normal vault file set. Record content hash, size, ETag, last-known state, path moves, and deletion tombstones. Retain tombstones long enough for offline devices to sync, then expire them safely.

The manifest must be excluded from normal file listings and updated with a concurrency check so two devices cannot silently overwrite each other's state.

### 5. Complete conflict and move handling

- Detect both-sides-changed conflicts relative to the shared baseline instead of relying only on timestamps.
- Add keep-local, keep-remote, keep-both, skip, and review-later actions.
- Use content hashes to propose moves or renames where appropriate.
- Never silently replace a conflicting file during first reconciliation.

### 6. Coordinate deletion, binary, and atomic-transfer work

- Implement reversible remote trash and honor `confirmBeforeDelete` and `moveToTrash`.
- Add binary-safe local and WebDAV reads/writes.
- Encode WebDAV path segments safely.
- Use the T9 temporary-write and rename strategy for local and remote writes.

### 7. Add reliability tests

Cover first syncs, stale-device deletions, tombstones, all direction modes, conflict choices, partial failures, index invalidation, binary round trips, cancellation, and remote trash behavior. Add the Chinese-learning-folder scenario as a manual acceptance test.
